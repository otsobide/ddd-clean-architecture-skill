# CQRS

**Command Query Responsibility Segregation (CQRS)** splits every operation of the system into one of two kinds:

- **Commands** change state.
- **Queries** read state.

Each kind travels its own path: its own message type, its own handler, and its own bus. A single use case is never both.

> **Golden rule: a command changes state and returns no data. A query returns data and changes nothing.**

## Why CQRS

- **Explicit intent.** `CreateProductCommand` says what the caller wants. A generic `save(product)` does not.
- **Small, focused handlers.** A handler that creates only creates. Nothing mixes read logic with write logic, and a read can never trigger a side effect by accident.
- **Decoupled entry points.** HTTP controllers, CLI commands, and message consumers only know the bus and the message. They never depend on use case internals, so the same use case can be triggered from any of them.
- **Independent evolution.** Reads and writes can be optimized separately. Reads can later move to dedicated read models (projections) without touching the write side.

CQRS does **not** require separate databases, event sourcing, or asynchronous processing. The baseline is in-process: same model, same storage, two clearly separated paths.

## Core concepts

| Concept | Role |
|---|---|
| **Command** | Immutable message expressing an intent to change state |
| **Command handler** | Receives exactly one command type and delegates to an application service |
| **Command bus** | Routes a command to its single registered handler |
| **Query** | Immutable message asking for data |
| **Query handler** | Receives exactly one query type, delegates, and maps the result to a response DTO |
| **Query bus** | Routes a query to its single registered handler and returns the response |
| **Response** | Plain DTO returned by a query, built from primitives and never containing domain objects |
| **Application service** | The use case itself (`ProductCreator`, `ProductFinder`). Orchestrates the domain: repositories, aggregates, event publishing |

---

## Commands vs queries

| | Command | Query |
|---|---|---|
| Purpose | Change state | Read state |
| Name | Imperative: `CreateProductCommand`, `RenameProductCommand` | Question: `FindProductQuery`, `SearchProductsQuery` |
| Returns | Nothing (`()`), or an error | A response DTO, or an error |
| Side effects | Yes: persistence and domain events | **None** |
| Publishes domain events | Yes, after the state change succeeds | Never |
| Handlers per message | Exactly one | Exactly one |
| Typical HTTP verbs | `POST`, `PUT`, `PATCH`, `DELETE` | `GET` |

## Rules

1. **Commands return no data.** Only success or failure. If the caller needs the new entity, it already has the identifier and can issue a query.
2. **Identifiers are generated by the caller.** The client or entry point generates the ID (for example a UUID v4) and puts it in the command. This is what makes rule 1 possible.
3. **Queries have no side effects.** No writes, no domain events, no "find or create", no "update last access".
4. **Domain objects never cross the bus on the way out.** Query handlers map aggregates to response DTOs made of primitives. Callers never receive an aggregate.
5. **One handler per message.** Each command or query type has exactly one handler. (Domain events are the opposite: many subscribers per event.)
6. **Handlers are thin.** A handler unpacks the message, calls the application service, and maps the result. Business logic lives in aggregates and application services, never in handlers.
7. **Messages are immutable data carriers.** Commands and queries have no behaviour. Their fields are Value Objects, so an invalid message cannot be built (see [Value Objects](value-objects.md)).
8. **Handlers never dispatch other commands.** If something must happen after a state change, publish a domain event and react to it (see [Domain Events](domain-events.md)).
9. **The bus is a port.** Bus traits live in the shared domain. Implementations (in-memory, broker-backed...) live in infrastructure. Entry points depend only on the traits.

## Flow

### Command

```
Entry point (HTTP, CLI, consumer)
  │  builds CreateProductCommand from validated Value Objects
  │
  └── CommandBus::dispatch(Box<dyn Command>)
        │  routes by command type
        │
        └── CreateProductCommandHandler::handle(command)
              │
              └── ProductCreator::execute(id, name)
                    ├── Product::create(id, name)
                    ├── ProductRepository::save(&product)
                    └── publish domain events (after the save succeeds)

Result<(), CommandBusError>  ──►  entry point maps it (201 / 409 / 500 ...)
```

### Query

```
Entry point
  │  builds FindProductQuery
  │
  └── QueryBus::ask(Box<dyn Query>)
        │  routes by query type
        │
        └── FindProductQueryHandler::handle(query)
              │
              ├── ProductFinder::execute(id) ──► Product (aggregate)
              └── maps Product ──► FindProductResponse (DTO)

Result<FindProductResponse, QueryBusError>  ──►  entry point maps it (200 / 404 / 500 ...)
```

## Use case layout and naming

Each use case gets its own folder under `application/`, named `<verb>_<noun>`:

```
product/
└── application/
    ├── create_product/
    │   ├── create_product_command.rs          # CreateProductCommand
    │   ├── create_product_command_handler.rs  # CreateProductCommandHandler
    │   └── product_creator.rs                 # ProductCreator (application service)
    └── find_product/
        ├── find_product_query.rs              # FindProductQuery
        ├── find_product_query_handler.rs      # FindProductQueryHandler
        ├── find_product_response.rs           # FindProductResponse (DTO)
        └── product_finder.rs                  # ProductFinder (application service)
```

| Concept | Pattern | Example |
|---|---|---|
| Command | `VerbNounCommand` | `CreateProductCommand` |
| Command handler | `VerbNounCommandHandler` | `CreateProductCommandHandler` |
| Query | `VerbNounQuery` | `FindProductQuery` |
| Query handler | `VerbNounQueryHandler` | `FindProductQueryHandler` |
| Query response | `VerbNounResponse` | `FindProductResponse` |
| Application service | `NounVerber` | `ProductCreator`, `ProductFinder`, `ProductRenamer` |

## Building blocks in Rust

The CQRS building blocks live in a shared crate: traits in `domain/`, implementations in `infrastructure/`.

### Command side

```rust
// shared cqrs: command/domain/command.rs

use std::any::{type_name, Any, TypeId};

/// Type-erasure helper so commands can travel as `Box<dyn Command>`.
/// Implemented automatically for every `Any + Send + Sync` type.
pub trait AnyCommand: Any + Send + Sync {
    fn into_any(self: Box<Self>) -> Box<dyn Any + Send + Sync>;
    fn command_type_id(&self) -> TypeId;
    fn command_name(&self) -> &'static str;
}

impl<T: Any + Send + Sync> AnyCommand for T {
    fn into_any(self: Box<Self>) -> Box<dyn Any + Send + Sync> {
        self
    }

    fn command_type_id(&self) -> TypeId {
        TypeId::of::<T>()
    }

    fn command_name(&self) -> &'static str {
        type_name::<T>()
    }
}

/// Marker trait: a type that can be dispatched through a `CommandBus`.
pub trait Command: AnyCommand {}
```

```rust
// shared cqrs: command/domain/command_handler.rs

use async_trait::async_trait;

use super::command::Command;

/// Handles exactly one command type `C`. Returns no data: only success or a domain error.
#[async_trait]
pub trait CommandHandler<C: Command>: Send + Sync {
    type Error: std::error::Error + Send + Sync + 'static;

    async fn handle(&self, command: C) -> Result<(), Self::Error>;
}
```

```rust
// shared cqrs: command/domain/command_bus_error.rs

#[derive(Debug, thiserror::Error)]
pub enum CommandBusError {
    #[error("no handler registered for command {0}")]
    HandlerNotFound(&'static str),

    #[error("a handler is already registered for command {0}")]
    HandlerAlreadyRegistered(&'static str),

    /// The handler ran and returned its domain error. Callers can downcast it.
    #[error(transparent)]
    Handler(Box<dyn std::error::Error + Send + Sync>),
}
```

```rust
// shared cqrs: command/domain/command_bus.rs

use async_trait::async_trait;

use super::command::Command;
use super::command_bus_error::CommandBusError;

#[async_trait]
pub trait CommandBus: Send + Sync {
    async fn dispatch(&self, command: Box<dyn Command>) -> Result<(), CommandBusError>;
}
```

### Query side

The query side mirrors the command side. The differences: handlers declare a `Response`, and the bus returns that response type-erased.

```rust
// shared cqrs: query/domain/query.rs
// `AnyQuery` is identical to `AnyCommand` (into_any, query_type_id, query_name).
pub trait Query: AnyQuery {}
```

```rust
// shared cqrs: query/domain/query_handler.rs

#[async_trait]
pub trait QueryHandler<Q: Query>: Send + Sync {
    type Response: Send + Sync + 'static;
    type Error: std::error::Error + Send + Sync + 'static;

    async fn handle(&self, query: Q) -> Result<Self::Response, Self::Error>;
}
```

```rust
// shared cqrs: query/domain/query_bus.rs

#[async_trait]
pub trait QueryBus: Send + Sync {
    /// Returns the handler's response type-erased. The caller downcasts it
    /// to the response type declared by the handler.
    async fn ask(&self, query: Box<dyn Query>) -> Result<Box<dyn Any + Send + Sync>, QueryBusError>;
}

// `QueryBusError` mirrors `CommandBusError`: HandlerNotFound, HandlerAlreadyRegistered, Handler(..).
```

## In-memory buses

The bus keeps one type-erased handler function per message type, keyed by `TypeId`. Handlers are registered once at startup. At dispatch time the bus looks up the message's `TypeId`, so routing is O(1) and needs no string keys or configuration.

```rust
// shared cqrs: command/infrastructure/in_memory/in_memory_command_bus.rs

use std::any::{type_name, Any, TypeId};
use std::collections::HashMap;
use std::future::Future;
use std::pin::Pin;
use std::sync::Arc;

use async_trait::async_trait;

type HandlerFuture = Pin<Box<dyn Future<Output = Result<(), CommandBusError>> + Send>>;
type HandlerFn = Box<dyn Fn(Box<dyn Any + Send + Sync>) -> HandlerFuture + Send + Sync>;

pub struct InMemoryCommandBus {
    handlers: HashMap<TypeId, HandlerFn>,
}

impl InMemoryCommandBus {
    pub fn new() -> Self {
        Self { handlers: HashMap::new() }
    }

    pub fn register<C, H>(&mut self, handler: H) -> Result<(), CommandBusError>
    where
        C: Command,
        H: CommandHandler<C> + 'static,
    {
        let type_id = TypeId::of::<C>();
        if self.handlers.contains_key(&type_id) {
            return Err(CommandBusError::HandlerAlreadyRegistered(type_name::<C>()));
        }

        let handler = Arc::new(handler);
        self.handlers.insert(
            type_id,
            Box::new(move |command| {
                let handler = Arc::clone(&handler);
                Box::pin(async move {
                    let command = command
                        .downcast::<C>()
                        .expect("the bus routes each command by its own TypeId");
                    handler
                        .handle(*command)
                        .await
                        .map_err(|error| CommandBusError::Handler(Box::new(error)))
                })
            }),
        );
        Ok(())
    }
}

#[async_trait]
impl CommandBus for InMemoryCommandBus {
    async fn dispatch(&self, command: Box<dyn Command>) -> Result<(), CommandBusError> {
        // Call through `as_ref()`: on a `Box<dyn Command>` the blanket impl would
        // otherwise resolve to the Box itself and return the Box's TypeId.
        let command_ref: &dyn Command = command.as_ref();
        let handler = self
            .handlers
            .get(&command_ref.command_type_id())
            .ok_or_else(|| CommandBusError::HandlerNotFound(command_ref.command_name()))?;

        handler(command.into_any()).await
    }
}
```

The in-memory query bus has the same shape. The only difference is that the stored closure boxes the handler's response:

```rust
handler
    .handle(*query)
    .await
    .map(|response| Box::new(response) as Box<dyn Any + Send + Sync>)
    .map_err(|error| QueryBusError::Handler(Box::new(error)))
```

> **Pitfall.** Never call `command_type_id()` (or `Any::type_id()`) directly on a `Box<dyn Command>`. The blanket `impl<T: Any + Send + Sync> AnyCommand for T` also covers the `Box`, so method resolution picks the Box's impl and returns `TypeId::of::<Box<dyn Command>>()`. No handler ever matches that. Always go through `as_ref()` or `&*command`.

## Command use case example

```rust
// product/application/create_product/create_product_command.rs

pub struct CreateProductCommand {
    pub id: ProductId,
    pub name: ProductName,
}

impl Command for CreateProductCommand {}
```

```rust
// product/application/create_product/product_creator.rs

pub struct ProductCreator {
    repository: Arc<dyn ProductRepository>,
}

impl ProductCreator {
    pub fn new(repository: Arc<dyn ProductRepository>) -> Self {
        Self { repository }
    }

    pub async fn execute(&self, id: ProductId, name: ProductName) -> Result<(), ProductError> {
        let product = Product::create(id, name);
        self.repository.save(&product).await?;
        // Domain events are published here, only after the save succeeds.
        Ok(())
    }
}
```

```rust
// product/application/create_product/create_product_command_handler.rs

pub struct CreateProductCommandHandler {
    creator: ProductCreator,
}

impl CreateProductCommandHandler {
    pub fn new(creator: ProductCreator) -> Self {
        Self { creator }
    }
}

#[async_trait]
impl CommandHandler<CreateProductCommand> for CreateProductCommandHandler {
    type Error = ProductError;

    async fn handle(&self, command: CreateProductCommand) -> Result<(), ProductError> {
        self.creator.execute(command.id, command.name).await
    }
}
```

The handler adds no logic: it unpacks the command and delegates.

## Query use case example

```rust
// product/application/find_product/find_product_query.rs

pub struct FindProductQuery {
    pub id: ProductId,
}

impl Query for FindProductQuery {}
```

```rust
// product/application/find_product/find_product_response.rs

/// Plain DTO: primitives only, no domain types.
pub struct FindProductResponse {
    pub id: String,
    pub name: String,
}
```

```rust
// product/application/find_product/product_finder.rs

pub struct ProductFinder {
    repository: Arc<dyn ProductRepository>,
}

impl ProductFinder {
    pub fn new(repository: Arc<dyn ProductRepository>) -> Self {
        Self { repository }
    }

    /// Returns the aggregate. Mapping to a DTO is the handler's job.
    pub async fn execute(&self, id: ProductId) -> Result<Product, ProductError> {
        self.repository
            .search(&id)
            .await?
            .ok_or_else(|| ProductError::NotFound(id.value().to_string()))
    }
}
```

```rust
// product/application/find_product/find_product_query_handler.rs

pub struct FindProductQueryHandler {
    finder: ProductFinder,
}

impl FindProductQueryHandler {
    pub fn new(finder: ProductFinder) -> Self {
        Self { finder }
    }
}

#[async_trait]
impl QueryHandler<FindProductQuery> for FindProductQueryHandler {
    type Response = FindProductResponse;
    type Error = ProductError;

    async fn handle(&self, query: FindProductQuery) -> Result<FindProductResponse, ProductError> {
        let product = self.finder.execute(query.id).await?;

        Ok(FindProductResponse {
            id: product.id().value().to_string(),
            name: product.name().value().to_string(),
        })
    }
}
```

The finder returns the aggregate so it can be reused by other use cases. The handler is the boundary where the aggregate becomes a DTO.

## Wiring: the composition root

Handlers are built and registered once, at startup, in a single place: the composition root. Dependencies are injected manually as `Arc<dyn Trait>`.

```rust
let repository: Arc<dyn ProductRepository> = Arc::new(InMemoryProductRepository::new());

let mut command_bus = InMemoryCommandBus::new();
command_bus
    .register(CreateProductCommandHandler::new(ProductCreator::new(Arc::clone(&repository))))
    .expect("CreateProductCommandHandler registered twice");

let mut query_bus = InMemoryQueryBus::new();
query_bus
    .register(FindProductQueryHandler::new(ProductFinder::new(Arc::clone(&repository))))
    .expect("FindProductQueryHandler registered twice");

let command_bus: Arc<dyn CommandBus> = Arc::new(command_bus);
let query_bus: Arc<dyn QueryBus> = Arc::new(query_bus);
```

The command or query type is inferred from the handler's `CommandHandler<C>` / `QueryHandler<Q>` impl, so `register` needs no turbofish.

Registering a handler twice is a wiring bug, so failing fast at startup with `expect` is correct.

## Dispatching from an entry point

An entry point does four things:

1. Builds the message from validated Value Objects. Invalid input is rejected before touching the bus.
2. Dispatches the message through the bus.
3. For queries, downcasts the response to the handler's declared `Response` type.
4. Maps the result (or the downcast domain error) to its own protocol.

Actix-Web is shown below. A CLI command or a message consumer follows the same steps.

```rust
// HTTP adapter: register the buses as `web::Data<dyn CommandBus>` / `web::Data<dyn QueryBus>`
// App::new()
//     .app_data(web::Data::from(command_bus.clone()))
//     .app_data(web::Data::from(query_bus.clone()))

#[derive(Deserialize)]
pub struct CreateProductRequest {
    pub id: String,
    pub name: String,
}

#[post("/products")]
pub async fn create_product(
    command_bus: web::Data<dyn CommandBus>,
    body: web::Json<CreateProductRequest>,
) -> HttpResponse {
    let command = match (ProductId::new(&body.id), ProductName::new(&body.name)) {
        (Ok(id), Ok(name)) => CreateProductCommand { id, name },
        (Err(error), _) | (_, Err(error)) => {
            return HttpResponse::BadRequest().body(error.to_string())
        }
    };

    match command_bus.dispatch(Box::new(command)).await {
        Ok(()) => HttpResponse::Created().finish(),
        Err(CommandBusError::Handler(error)) => match error.downcast_ref::<ProductError>() {
            Some(ProductError::AlreadyExists(_)) => HttpResponse::Conflict().body(error.to_string()),
            _ => HttpResponse::InternalServerError().body(error.to_string()),
        },
        Err(error) => HttpResponse::InternalServerError().body(error.to_string()),
    }
}

#[get("/products/{id}")]
pub async fn find_product(
    query_bus: web::Data<dyn QueryBus>,
    path: web::Path<String>,
) -> HttpResponse {
    let id = match ProductId::new(path.into_inner()) {
        Ok(id) => id,
        Err(error) => return HttpResponse::BadRequest().body(error.to_string()),
    };

    match query_bus.ask(Box::new(FindProductQuery { id })).await {
        Ok(response) => {
            let product = response
                .downcast::<FindProductResponse>()
                .expect("FindProductQuery is answered with FindProductResponse");
            HttpResponse::Ok().json(json!({ "id": product.id, "name": product.name }))
        }
        Err(QueryBusError::Handler(error)) => match error.downcast_ref::<ProductError>() {
            Some(ProductError::NotFound(_)) => HttpResponse::NotFound().body(error.to_string()),
            _ => HttpResponse::InternalServerError().body(error.to_string()),
        },
        Err(error) => HttpResponse::InternalServerError().body(error.to_string()),
    }
}
```

The response downcast cannot fail when the wiring is correct: each query type has one handler, and that handler has one `Response` type. A failing downcast is a programming error, so `expect` is appropriate.

## Testing

| What | How |
|---|---|
| Application services (`ProductCreator`, `ProductFinder`) | Unit tests with hand-written mocks of the repository and event bus. This is where the business behaviour is verified. |
| Handlers | Thin by design. Covered indirectly by the end-to-end tests, with no dedicated unit tests needed. |
| Bus implementation | Tested once in the shared crate: routing, `HandlerNotFound`, `HandlerAlreadyRegistered`, error propagation. |
| Full path | End-to-end tests through the real entry point, with in-memory repositories wired in the composition root. |

## Anti-patterns

| Anti-pattern | Fix |
|---|---|
| Command that returns the created entity or its generated ID | The caller generates the ID, then issues a query if it needs data |
| Query that writes ("find or create", "touch last access") | Split it into a command and a query |
| Business rules inside a handler | Move them to the aggregate or the application service |
| Query handler returning an aggregate | Map it to a response DTO of primitives |
| One handler for several messages, or several handlers for one message | Exactly one handler per command or query |
| Handler dispatching another command | Publish a domain event and react with a subscriber |
| Entry point calling the application service directly | Go through the bus, so entry points depend only on bus traits and messages |
| Command or query fields as raw primitives | Use Value Objects, so invalid messages cannot exist |

## Checklist

- [ ] The use case is either a command (writes, returns `()`) or a query (reads, no side effects), never both
- [ ] The use case has its own folder `application/<verb>_<noun>/`
- [ ] Message, handler, application service and (for queries) response follow the naming conventions
- [ ] Message fields are Value Objects; IDs for new aggregates come from the caller
- [ ] The handler only unpacks, delegates, and maps
- [ ] The query handler maps the aggregate to a primitive-only response DTO
- [ ] Domain events are published by command use cases only, after the state change succeeds
- [ ] The handler is registered once in the composition root
- [ ] The entry point builds the message, dispatches it, and maps results and domain errors to its protocol
